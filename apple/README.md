# Apple app

A Swift app for iPhone, iPad and Mac: the rows are edited natively and the
graph is drawn in Metal. The site's renderer and language (`web/`, `lib/`) are
being ported to Swift a piece at a time; what a piece doesn't cover yet, the
app doesn't do yet.

- `Equation/` — the app (SwiftUI, one multiplatform target, generated by
  [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`).
- `EquationCore/` — a Swift package of three libraries. `EquationCore` is the
  language, ported from `lib/` a stage at a time; no Foundation, so it can
  also build for WebAssembly. `EquationRender` is the Metal renderer, ported
  from `web/render2d.ts` and `web/render3d.ts`. `EquationAssist` is Ask's
  lookups (list_kinds, kind_examples, shape, search_functions, function_doc),
  ported from `lib/assistant-tools.ts`.
- `tools/` — `app-data.ts`, the data the app bundles; `web-shot.ts`, a picture
  of a graph as the site draws it.
- `corpus/` — records what the TypeScript suite asks the parser, and what the
  analyzer makes of every example and of targeted documents, so the Swift
  port is held to the same answers.
- `evals/` — Ask's evals: the tasks, the service that grades them, the runner.

The TypeScript the Apple side adds outside `apple/` is what Ask answers from:
`docs/reference/` (the language reference its lookups and instructions are
generated from), `lib/reference.ts`, `lib/assistant-tools.ts`,
`lib/assistant-instructions.ts` and `scripts/reference.ts`. The site does not
use them: its own reference, `web/public/llms.txt`, is written by hand, so a
change to the language is described in both.

## Build

```sh
pnpm app:data                         # the examples and Ask's reference, into Equation/Data
xcodegen -s apple/Equation/project.yml
open apple/Equation/Equation.xcodeproj
```

`pnpm app:data` (`tools/app-data.ts`) writes three files, which the app
copies as they are: `examples.json`, the Examples menu (`web/examples.ts`);
`assistant.json`, what Ask's lookups answer from (the reference in
`docs/reference`, with the menu's examples by kind and by function); and
`language.json`, what they read from the language itself (the function
table, each kind's meaning). Run it again after changing any of those.

`pnpm reference` (`scripts/reference.ts`) writes
`Equation/Sources/Instructions.swift`, Ask's instructions, from
`lib/assistant-instructions.ts` and the reference's list of kinds; it is
checked in, and `lib/reference.test.ts` fails while it is out of date. Every
change to that text is a change to measure (see Ask evals).

Debug builds open straight onto a graph, skipping the document browser, with
`EQUATION_SCRATCH` set (rows separated by `;`):

```sh
SIMCTL_CHILD_EQUATION_SCRATCH='y = sin(a x); a = 2' xcrun simctl launch booted io.equation.app
```

## The graph view

`GraphContent.swift` is a document as the view shows it: `EquationRender`'s
`GraphPanels` (the panels, their layout, windows, shared axes and 2D scenes —
what metal-shot draws from the same rows) with each 3D panel's `Document3D`
and the display toggles rows are shown with (a level set's "all levels", a
sequence's partial sums, a field's streamlines and arrows in space; they are
the view's, kept by row in `GraphModel`, not saved). `MetalCanvas.swift`
draws a frame of them (`FrameRenderer`: 3D panels in a multisampled pass of
their own, copied in among the 2D ones), owns the windows, the cameras, the
clock and the run of the document's states (`StateStepper`), and moves them;
`GraphGestures.swift` hands it the platform's events. A window, a camera or
a point moved by hand rewrites its row, as on the site, and in a Mac
document window everything one gesture rewrites is one undo step.

Ask's `get_graph`, `set_graph` and `check` describe each row as the site
does (`EquationRender` `RowReport.swift`, lib/assistant-tools.ts
`describeRow` ported and held to it by fixture: `pnpm swift:reports`).

In debug builds `EQUATION_SCENE3D` (a `Graph3D`'s JSON, the path of one, or
`demo`) draws a scene written down in the panel with a `camera(…)` row, or
the first, in place of the builder's. `EQUATION_SCRIPT` plays gestures,
commands and Ask's tools and takes pictures without a hand or a screen (the
steps are listed in `GraphGestures.swift`); `-ApplePersistenceIgnoreState
YES` keeps a killed run's saved windows from holding the next one's back:

```sh
open -n Equation.app --env EQUATION_SCENE3D=demo \
  --env EQUATION_SCRATCH='camera(-1, 0.5, 12); --- right 40%; y = sin(x)' \
  --env EQUATION_SCRIPT='drag 300 400 400 440; wait 1; shot orbit; rows after'
```

## The renderer

`EquationRender` keeps the site's shaders as the site writes them. They are
GLSL; `GLSL.swift` wraps a fragment shader's source so that it compiles as
Metal (GLSL's names defined, its uniforms and `gl_FragCoord` made fields of a
struct whose methods are the shader's functions), and `Frag2D.swift` holds
each shader function of `web/render2d.ts` under its own name, its text copied
and its holes filled the same way. `lib/glsl.ts`'s helper prelude is written
into the package as it is (`pnpm swift:prelude`). So a shader is ported by
copying it, and the language's Swift port emits the same GLSL text the
TypeScript does, which a fixture can check to the byte.

`Render2D.swift` has the site's scene types (`View2D`, `Layers2D`, …) field
for field, and `Renderer2D.render` draws them in the site's order. What is
drawn with a 2D context over the shader passes (axis numbers, a lattice's
labels, points, polylines, clouds, bars, regions, a graph's vertices, text) is `Overlay2D.swift`, in CoreGraphics and CoreText; a `Scene2D` carries
it as `overlay`. A mapped axis (`view(x = 10^X)`) is the core's
`AxisMap.swift`, which also rewrites a row for one; its ticks are
`AxisTicks.swift`, and `MapOverlay.swift` carries a row's overlay through one.

`Graph2D` is one panel filling a frame; `GraphPanels` (EquationRender) is a
document as its panels, split by `---` rows (the core's `Panels.swift`), each
with its box, its window and the axes it shares. A document with states
(`a' = …`) has a run, the core's `StateStepper`, which whoever draws frames
owns, advances to each frame's time and hands to `scene(at:…run:)`; it holds
the states' values and what `trail(…)` rows have seen.

To see what the renderer draws without the app, and set it beside the site:

```sh
cd apple/EquationCore
swift run metal-shot --out metal.png "y = sin(x)" "x^2 + y^2 = 9"   # or --scene scene.json, a Scene2D
node ../tools/web-shot.ts --out web.png "y = sin(x)" "x^2 + y^2 = 9"  # the live site, same size and theme
swift run metal-shot --diff web.png metal.png --out diff.png
```

`Render3D.swift` and `Renderer3D.swift` are `web/render3d.ts` the same way:
its scene types, and its vertex and fragment shaders (`Frag3D.swift`)
compiled as Metal by `GLSL3D.swift`. A document with a row in space
(`Graph.kind(of:)`) is drawn through `Document3D.swift`, which builds the
scene from the rows' plans as `web/scene.ts` `renderPanel` does: shaders for
surfaces and clouds, and what the site samples, traces or solves on the CPU
(curves and tubes, a field's streamlines, intersections, systems).

```sh
swift run metal-shot --out metal.png "z = sin(x) cos(y)" "camera(-pi/3, 0.5, 9)"
```

`tools/scene3d.ts` builds the same scene with the TypeScript pipeline, as
JSON metal-shot also draws (`--scene scene.json`); `corpus/scenes3d.ts`
records it for a set of documents, and `Document3DConformance` holds the
Swift builder to it:

```sh
node --experimental-transform-types ../tools/scene3d.ts "z = sin(x) cos(y)" "camera(-pi/3, 0.5, 9)" > scene.json
swift run metal-shot --out metal.png --scene scene.json
```

The site is the reference for what a graph looks like, not a pixel target:
where Metal offers a better trade (precision, speed, antialiasing), take it,
and say so where the code departs.

## Core conformance

```sh
pnpm swift:test    # re-record the corpus from the TypeScript suite, then swift test
```

The fixtures are recorded from the checkout's own `lib/` and `web/examples.ts`,
so the port is held to the language of the commit it is built from: after
merging `main`, re-record, and port what differs. `AnalysisConformanceTests`
prints the coverage (rows the port reads of all it is shown, by example row
and by whole example document) and what holds the rest back;
`ANALYSIS_WHY=<text>` and `ANALYSIS_UNSUPPORTED=<name prefix>` list the rows.
A row is either read as the site reads it or reported as not supported yet.

The corpus includes what Ask's lookups answer in TypeScript to a few thousand
requests (`corpus/lookups.ts`: every kind, shape and function by each of its
names, with misspellings, phrases and misses), which `EquationAssist` must
answer the same to the character: the evals below score what the tools
return. `pnpm swift:lookups` records that part alone, after a change to the
reference, the examples or `lib/assistant-tools.ts`.

## Ask evals

```sh
pnpm app:eval                     # every task in apple/evals/tasks.ts, 5 runs each, on-device
pnpm app:eval --runs 1 --task unit-cube
pnpm app:eval --sampling greedy   # as the app answers; evals sample by default
pnpm app:eval --model openai              # hosted baseline, gpt-5.5 (--openai-model to change)
node --experimental-transform-types scripts/reference.ts --llms > reference.txt   # the reference as one file
pnpm app:eval --model openai --reference reference.txt   # the whole reference in context, no lookups
node --experimental-transform-types apple/evals/report.ts apple/evals/results/a.json apple/evals/results/b.json
```

A Swift runner (`apple/evals/Runner.swift`) asks the on-device model each
task's request with the app's own instructions and tools
(`Equation/Sources/Assistant.swift`, and Instructions.swift, which `pnpm
reference` writes from lib/assistant-instructions.ts); the tools act on a Node service
(`apple/evals/service.ts`) running the real analyzer, which also grades the
result. Results are saved in `apple/evals/results/`; see
`apple/evals/RESULTS.md`.

`--model openai` runs the same instructions, prompts and tools on OpenAI's
Chat Completions API: each tool's schema is its `@Generable` arguments
encoded as JSON Schema, and each call runs the tool's own code. The key is
`OPENAI_API_KEY` from the environment, or that line of the checkout's
`.dev.vars` (a worktree reads the main checkout's). Rate limits and server
errors are retried with backoff. With `--reference <file>` the model gets that
file after the app's instructions (`referenceInstructions`) in place of the
lookup tools, keeping get_graph, set_graph, move_view, animate_slider and
check; it doesn't fit the on-device model's 8K context. A full run (175 episodes) costs a few
dollars; the results record each run's tokens, cached and reasoning tokens
included, and the model's snapshot id.
